## What needs the developer account

None of this can be produced from a shell; without it no Mac App Store build exists.

1. **Apple Developer Program** membership (99 €/year).
2. Certificate **Apple Distribution** (portal → Certificates → Apple Distribution, or
   Xcode → Settings → Accounts → Manage Certificates). Signs the app.
3. Certificate **Mac Installer Distribution** / "3rd Party Mac Developer Installer"
   (`-p basic` policy; `security find-identity -v -p basic` shows it). Signs the pkg.
4. **App ID** `com.zopyx.usbscope` with the App Store provisioning profile
   (`usbscope_mas.provisionprofile`). The script embeds it as
   `Contents/embedded.provisionprofile` and prints its SHA-256.
5. **App Store Connect** app record (see the metadata below).

## Build and sign

```console
make artifacts          # app bundle + DMG for direct distribution
make mas-pkg-dry        # review the commands first
make mas-pkg            # the real thing (needs 2 + 3 + 4 above)
```

`make mas-pkg` runs, in this order:

```console
# 1. embed the profile
cp usbscope_mas.provisionprofile dist/usbscope.app/Contents/embedded.provisionprofile
# 2. sign the app with the sandbox entitlements
codesign --force --deep --timestamp --options runtime \
    --entitlements assets/entitlements/usbscope.entitlements \
    --sign "Apple Distribution: … (TEAMID)" --identifier com.zopyx.usbscope dist/usbscope.app
# 3. verify what was signed
codesign --verify --deep --strict --verbose=2 dist/usbscope.app
codesign -d --entitlements - dist/usbscope.app      # must list com.apple.security.app-sandbox
# 4. build and verify the installer
productbuild --component dist/usbscope.app /Applications \
    --sign "3rd Party Mac Developer Installer: … (TEAMID)" dist/usbscope-<version>-mas.pkg
pkgutil --check-signature dist/usbscope-<version>-mas.pkg
```

The script also refuses to continue when the signature does not carry the sandbox
entitlement — a package without it is rejected by App Store Connect.

## Upload

```console
# Transporter.app (GUI) — or the command line with an App Store Connect API key:
xcrun altool --upload-app -f dist/usbscope-<version>-mas.pkg -t macos \
    --apiKey "$ASC_KEY_ID" --apiIssuer "$ASC_ISSUER_ID"
```

Then in App Store Connect → *My Apps* → usbscope → *Build* pick the uploaded build,
answer the compliance question (already answered by the Info.plist key), and submit.

## The open technical question: sandbox vs. the data sources

This is the one thing that decides whether the App Store version works, and it cannot
be answered on this machine.

usbscope currently learns everything by spawning two system tools
(`/usr/sbin/system_profiler`, `/usr/bin/ioreg`). A sandboxed app may spawn them, but
the children inherit the sandbox — whether they can still read the IO registry has to
be verified with a real App Store signature.

Measured here: a plain binary with `com.apple.security.app-sandbox` and an ad-hoc
signature **traps at launch** (`Trace/BPT trap: 5`), while the same binary without the
entitlement runs and reads files outside its container. The sandbox cannot initialise
without an Apple-issued signature plus provisioning profile, so no local sandbox test
is possible — the test needs steps 1–4 above.

**Plan B if the sandbox blocks the subprocesses:** read the IO registry in-process.
The parsing already exists — `src/usbscope/sources/ioreg.py` walks the
`IOPort`/`IOAccessory` plane (`AppleHPMInterface`, `AppleTypeCPhyInterface`,
`AppleUSBHostController`) and does not care where the plist came from. Only the
*reader* would change: `pyobjc-framework-IOKit` → `IOServiceGetMatchingServices` +
`IORegistryEntryCreateCFProperties` → the same dictionary the parser already
understands, with the `system_profiler` data reduced to what IOKit offers (or dropped
for the sandboxed build). Effort: roughly a day including tests; it also removes the
two subprocess calls, which makes the app start faster.
